# 接手清单与验收要求

## 必须先核实的现状

平台状态来自用户提供的截图与反馈，助手没有取得网页编辑权限。先打开现有意图流检查，避免重复创建或覆盖用户后续修改。

- [ ] 从课程入口进入正确的 BIP 租户，找到「智链销-销售查询」与「销售数据查询」。
- [ ] 核对画布已有节点、连线、未保存修改及是否发布。
- [ ] 核对代码节点输入 jsonText 是否真正引用模型 output，而非固定文本或未解析的变量表达式。
- [ ] 核对代码是否与 src/parse-query.js 一致。用户最终截图只展示了代码后半部分和字段列表，不能保证逐字相同。
- [ ] 核对条件分支引用的是该执行路径上游的 queryStatus。
- [ ] 核对 API 日期字段仍为固定值还是已替换为变量。

## 待完成工作

1. 完成 rawQuery → 模型 output → jsonText 的引用。
2. 完成 queryStatus == ready 的条件分支及 clarification 回复路径。
3. 完成 API 的 from、to、商品参数绑定，核对鉴权配置，不将密钥写入提示词或仓库。
4. 从 API 定义确认商品参数完整名称、空值语义、日期包含关系、指标支持和必填参数。
5. 确认 API 节点 success 为布尔值，成功回复 answer 与 source_note，失败路径明确报告未取得数据。
6. 核对节点异常（超时、网络、执行失败）能否经过业务失败分支；不要假定异常中断会自动输出 success=false。
7. 调试后保存、按平台要求发布意图流，并确认智能体实际关联这条意图流。

## 指标选择尚未实现

目前解析代码没有 metric 字段，API 截图中的 metric 固定为 sales。因此当前方案仅准备先跑通销售额路径，不能宣称已自动支持退货额和净销售额。

后续若实现自动选择：在模型输出、解析代码、API 绑定和测试中同时新增并校验 metric，枚举按截图 API 描述为 sales / returns / net。用户一次要求三个指标时，应先确认 API 是否支持批量指标；不支持时执行三次查询再按同一期间与范围合并，不能传递未确认的 all、逗号串或数组。

## 其他明确限制

- 原提示词要求明确的绝对日期；「本月」「最近」等相对日期会要求补充。
- 商品范围缺失时会要求补充；不能默认为全部商品。
- 商品名称由用户提供；不能由模型虚构商品 ID。
- JSON 代码只校验已经提取的日期和范围，不能证明这些字段忠实反映原问题。需用完整链路测试检查提取质量。
- clarification 路径设计为要求用户重新发送完整查询条件，没有实现可靠的跨轮槽位补全。
- 同时请求多个商品、明细分页、跨门店汇总和额外业务维度尚未设计。

## 验收测试

| 用例 | 预期 |
|---|---|
| 明确日期＋一个真实商品＋销售额 | API 入参正确，回复来自真实 API，附带来源 |
| 明确日期＋全部商品 | 按已确认的接口“全部”规则查询 |
| 缺少日期或年份 | 提示补充，不发起数据查询 |
| 缺少商品范围 | 提示补充，不扩大查询范围 |
| 开始日期晚于结束日期 | 提示修正，不发起查询 |
| 2026-02-30 等不存在的日期 | 提示修正 |
| API 明确返回 0 | 显示 0 |
| API 无记录 | 显示无匹配记录，不能解释为 0 销售 |
| API 返回 success=false | 明确告知查询失败 |
| API 超时、授权失败或节点异常 | 进入已配置的失败处理，不显示虚构结果 |
| 用户要求退货额／净销售额 | 若指标功能尚未完成，不能返回 sales 冒充用户所需指标 |
| 用户要求库存、净利润、退款到账 | 说明该 API 不提供对应数据，不生成数字 |

需要保存可复查的脱敏调试记录：用户问题、节点入参、API 返回、最终回复和失败路径。

## 代码异常排查记录

曾出现平台统一提示「代码块执行异常，请检查代码块」。原解析代码、固定返回示例、无引号示例均曾被报告失败；之后用户反馈「可以了」，输出结构已显示。未得到明确根因或详细异常日志。

不要把引号、代码服务、权限或网络中的任何一项写成已确认的根因。排查建议从新建的原始模板节点与已知常量输入开始，并查看平台实际错误详情。
